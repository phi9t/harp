# Session failure-mode audit — October 12, 2026

Source repository read: `e045d4a6ae2a5efaa53fab93a129b3a57098f7ad`.
Audit dates use America/Los_Angeles. Source timestamps remain UTC in the evidence files.
This is an observational audit of retained execution history. Recommendations are proposals, not implemented controls.

The highest-priority findings concern the relationship between a result and its evidence, followed by ownership and execution-state recovery. Checks sometimes passed a weaker condition than the claim made to the user. In other episodes, agents could not recover a recorded result, overstated retained failure evidence, or allowed verification work to interfere with another agent's checkout.

The audit documents **10 behavioral episodes and eight runtime categories**. All 10 behavioral episodes include a visible correction or recovery attempt. This does not establish final project success. The runtime database audit found **34 unexpected failed turns across 25 sessions**, within the retained structured-turn subset. Many sessions subsequently completed another turn.

The recommendations below are ordered by consequence and evidence strength. No provider ranking or corpus-wide behavioral failure rate is justified by this sample.

**Controls to prioritize**

| Priority | Proposed control | Demonstration required |
| --- | --- | --- |
| 1 | Bind each acceptance claim to its actual behavior and exact Candidate; issue a Check receipt with command, outcome, and log identity | The check rejects a relevant incorrect candidate; changing a text anchor or classification cannot make the unchanged faulty behavior pass |
| 2 | Store execution identity, terminal status, and exit code outside model context; seal each attempt's log | After compaction or restart, the lead retrieves the original result without rerunning; a retry cannot overwrite failure evidence |
| 3 | Enforce one writer per WorkspaceGeneration, including verification; tie watchers to owned Executions | Mutation tests cannot alter another writer's checkout; terminal or retired executions cannot leave indefinite owned watchers |
| 4 | Require an observation that distinguishes leading hypotheses before repeated fixes | The exact failing assertion and resolved runtime inputs are captured; the same behavioral check passes after the causal fix |
| 5 | Preflight provider capabilities and resource headroom; classify and bound retries | Invalid tool-choice values fail preflight; deterministic request errors stop unchanged retries; storage admission stops before critical record writes fail |
| 6 | Keep required review and rework pending under the admitted intent across turn boundaries | A ready worker advances through authorized follow-up without requiring the user to restate the request |

The control descriptions use this repository's glossary. They are recommendations for later design and testing. This audit changes no live workers, provider configuration, controller code, or engineering policy.

**Scope and method**

The source inventory contains 5,367 thread records: 2,953 TraeCLI, 1,927 Codex, 482 Claude, and five CLI threads with unresolved provider identity. It includes subagents, automated review workers, probes, and human-led sessions. It does not represent 5,367 independent user tasks.

The earlier inventory parsed 16.7 GB of transcript and CLI trace data. This audit combines structured runtime queries with targeted investigation of behavioral incidents. It does not claim a semantic review of every conversation.

The audit uses four steps: collect explicit error and correction candidates; inspect the request, action, result, and later recovery; deduplicate copied and inherited evidence; distinguish observed behavior from inferred cause. Three investigators examine runtime reliability, instruction following, and coordination separately. The lead reconciles their claims against original records and checks the audit's measurement limits.

The behavioral sample is purposive. Verified cases establish that a failure mode occurred; they do not estimate its frequency. Priority reflects consequence and the strength of the evidence, not a cross-provider failure-rate ranking.

**What counts as a finding**

A runtime finding requires an explicit execution error or a failed operation with its source identity. A behavioral finding requires the preceding requirement or claim, the actual action or observation, and enough subsequent context to distinguish correction from a new request. An assistant admission supports a case; where possible, a tool result corroborates it.

A process exit code, a completed transport call, a model's completion message, and acceptance of a Candidate describe different states. The audit keeps them separate. Expected red tests, grep misses, user interruptions, and appropriate policy refusals are not automatically agent mistakes.

**Measurement limits**

The stores were live during collection. They are not a transactionally consistent backup. Retention differs by provider and source. Native failed-turn counts use the native history database denominator, not all inventory records.

The earlier inventory's message, tool, and compaction counters are schema-dependent. Some modern Codex records use different event shapes, so a zero in those fields does not establish absence. These counters are not used as failure-rate denominators; the inventory summary now records this limitation.

There are 953 records with only prompts or metadata. Nine malformed JSON records occur in eight native transcript files. None is merely an incomplete final line at the audit snapshot. Also, 258 parsed artifacts contain more than one session metadata record. Counts must account for inherited history and copied evidence.

The AgentsView index is useful for recovery and search, but its heuristic outcomes are not acceptance evidence. For example, it flags tool-failure signals in 77 of 466 Claude records and zero of 1,878 Codex records. Different adapters and retained schemas prevent interpreting that contrast as relative reliability.
