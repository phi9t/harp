Read 2026-10-04. Research only for baseline06; no implementation, inference, account endpoint, login, auth-file read, checkout mutation, or native fixture rerun. The prior06 provider-readiness report was read first and is retained as `prior-readiness.md` (SHA256 `d2b65bfff0a06131cdfa5496b19228e81c3fae878f792633f03b67c1cb390e2c`). ## Decision

**The matching native auth contract is now source-established.** An existing managed native ChatGPT login can technically supply a **trusted-side, account-bound credential owner** for a custom-provider Responses relay without putting account credentials in the native control/tool realms. This is an implementation inference from the source, not an existing supported Corenius relay or a live-account qualification. Merely copying `access_token` from a host file is insufficient: refresh rotation, auth identity, workspace routing and exact native wire payload must remain coherent. The custom-provider/native-TUI no-account behavior remains established by the earlier retained actual model-free fixtures; it was not repeated here.

The published SIWC public-API flow is a different credential/route contract. There is no evidence here that an already stored native Codex token is a SIWC token or can be moved to its public endpoint. Source availability establishes native implementation behavior, not a published stability promise for third-party reuse of the ChatGPT backend.

## Routes, account identity and headers: source facts

1. Native managed `Chatgpt`/external `ChatgptAuthTokens` default provider base is `https://chatgpt.com/backend-api/codex`; API-key auth defaults to `https://api.openai.com/v1`. An explicitly configured base overrides either default. HTTP Responses appends `/responses` and sets `Accept: text/event-stream`. Thus the normal native ChatGPT route is `POST https://chatgpt.com/backend-api/codex/responses`, subject to workspace routing below. [Provider selection](https://github.com/openai/codex/blob/01fc69f4026735edfdf6789820549727a4867b11/codex-rs/model-provider-info/src/lib.rs#L420), [HTTP request](https://github.com/openai/codex/blob/01fc69f4026735edfdf6789820549727a4867b11/codex-rs/codex-api/src/endpoint/responses.rs#L130).

2. For the ordinary ChatGPT bearer branch, native sends `Authorization: Bearer <tokens.access_token>`, `ChatGPT-Account-ID: <tokens.account_id>`, and conditional `X-OpenAI-Fedramp: true`. At browser login, `account_id` is captured from the ID-token's `chatgpt_account_id` auth claim. The bearer is the **access token**, not the ID token or refresh token. Source also supports other first-party mechanisms such as agent identity; this report's relay profile is the ordinary managed ChatGPT bearer branch, not blanket support for every auth mode. [Token/account accessor](https://github.com/openai/codex/blob/01fc69f4026735edfdf6789820549727a4867b11/codex-rs/login/src/auth/manager.rs#L580), [header builder](https://github.com/openai/codex/blob/01fc69f4026735edfdf6789820549727a4867b11/codex-rs/model-provider/src/bearer_auth_provider.rs#L30), [login persistence](https://github.com/openai/codex/blob/01fc69f4026735edfdf6789820549727a4867b11/codex-rs/login/src/server.rs#L839).

3. Native app-server's first-party ChatGPT path discovers the selected account through `GET <chatgpt-base>/wham/accounts/check` (normally `/backend-api/wham/accounts/check`). It requires exactly one matching account, validates `workspace_backend_origin`, and recognizes routing override `NO_CONSTRAINT`, `us`, or `us_cr`. It rejects missing/duplicate account, discovery failure, account change, invalid route, and managed-required-origin conflict. A discovered route replaces only the origin, preserves the Responses path, injects `x-openai-account-routing-override` for `us`/`us_cr`, and rejects redirects. Discovery is credential-generation/account/base keyed, serialized, and invalidated on credential changes. CLI paths without the app-server resolver retain prior routing behavior. [Discovery](https://github.com/openai/codex/blob/01fc69f4026735edfdf6789820549727a4867b11/codex-rs/app-server/src/request_processors/account_processor/workspace_routing.rs#L289), [route validation](https://github.com/openai/codex/blob/01fc69f4026735edfdf6789820549727a4867b11/codex-rs/app-server/src/request_processors/account_processor/workspace_routing.rs#L427), [application](https://github.com/openai/codex/blob/01fc69f4026735edfdf6789820549727a4867b11/codex-rs/model-provider/src/workspace_routing.rs#L39).

4. A custom provider with `requires_openai_auth=false` and no provider auth explicitly receives an unauthenticated provider: ambient native auth is not inherited. Therefore sterile native `model_provider="corenius-relay"` can send its native wire request to the relay while only the trusted side supplies upstream account headers. Setting `requires_openai_auth=true` inside a tool-visible native realm would defeat this separation. [Explicit auth selection and its tests](https://github.com/openai/codex/blob/01fc69f4026735edfdf6789820549727a4867b11/codex-rs/model-provider/src/auth.rs#L197).

5. Native also emits protocol/diagnostic headers: `originator`, User-Agent, built-in provider `version`, `session-id`, `thread-id`, `x-client-request-id`, optional beta/turn metadata, and **`x-codex-turn-state`** round-tripped within a turn. Responses Lite sends **`x-openai-internal-codex-responses-lite: true`** even for a custom provider. These are observed native compatibility inputs, not proof that every one is a server-mandatory authentication header. Relay policy must distinguish bounded native protocol headers from account/authority headers that it overwrites. `OpenAI-Organization`/`OpenAI-Project` come from optional built-in-provider environment mappings; they are not substitutes for ChatGPT account identity. [Lite/turn headers](https://github.com/openai/codex/blob/01fc69f4026735edfdf6789820549727a4867b11/codex-rs/core/src/client.rs#L2317), [request options](https://github.com/openai/codex/blob/01fc69f4026735edfdf6789820549727a4867b11/codex-rs/core/src/client.rs#L1350), [session headers](https://github.com/openai/codex/blob/01fc69f4026735edfdf6789820549727a4867b11/codex-rs/codex-api/src/requests/headers.rs#L5).

## Refresh, persistence and concurrency: source facts

- Auth supports file, keyring/auto, and ephemeral stores. Production source says to prefer `AuthManager` over raw stored-payload loading. It handles configured auth restrictions and environment/source precedence. No actual local store was inspected.
- Managed ChatGPT proactively refreshes when access-token JWT expiry is within **5 minutes**, or, when no usable expiry is parsed, when `last_refresh` is older than **8 days**. Failure at this proactive accessor logs and returns the earlier snapshot; the relay must define its own fail-closed/error policy rather than assume this accessor guarantees a fresh token.
- Refresh posts JSON to default **`https://auth.openai.com/oauth/token`** with `grant_type="refresh_token"`, native public client ID `app_EMoamEEZ73f0CkXaXp7hrann`, and refresh token; no `resource` is added in this native refresh flow. Endpoint/client-ID overrides exist in source and must not be accepted from workers. Optional returned `id_token`, `access_token`, and replacement `refresh_token` update the selected store; `last_refresh` is updated, then manager cache reloaded. Refresh does not rewrite saved `account_id` from the new ID token. The selected identity must remain pinned.
- Native401 recovery is bounded: guarded reload only if the stored account still matches; then token-authority refresh; then exhausted/error. API-key auth has no equivalent native OAuth recovery. External auth providers have a separate one-refresh path. Expired/reused/invalidated refresh tokens,401, or400 `invalid_grant` are permanent failures; transport/invalid JSON and other unclassified rejections are transient. Permanent failures are cached for the attempted auth until credentials change. [Refresh exchange/classification](https://github.com/openai/codex/blob/01fc69f4026735edfdf6789820549727a4867b11/codex-rs/login/src/auth/manager.rs#L1599), [401 state machine](https://github.com/openai/codex/blob/01fc69f4026735edfdf6789820549727a4867b11/codex-rs/login/src/auth/manager.rs#L1849), [expiry policy](https://github.com/openai/codex/blob/01fc69f4026735edfdf6789820549727a4867b11/codex-rs/login/src/auth/manager.rs#L3004).
- The refresh semaphore is **in-process and per AuthManager**, not a demonstrated cross-process lock. Proactive refresh holds it around guarded reload and refresh. The401 authority-refresh method takes the semaphore but calls authority refresh directly. File storage uses truncate/write/flush with creation mode0600; it does not use a file-lock/atomic-rename transaction in the inspected path. Thus separate consumers sharing or cloning one rotating refresh-token store are not proven safe. Reuse one trusted auth owner and explicitly coordinate any independent host-native refresher; adding a relay-local lock cannot make an unrelated native process obey it. [Manager locking](https://github.com/openai/codex/blob/01fc69f4026735edfdf6789820549727a4867b11/codex-rs/login/src/auth/manager.rs#L2844), [file save](https://github.com/openai/codex/blob/01fc69f4026735edfdf6789820549727a4867b11/codex-rs/login/src/auth/storage.rs#L195).
- Native request setup tracks credential revision and owner generation, rebuilding credentials/routing after refresh and rejecting an account switch during setup. Its managed auth adapter anchors account ID, ChatGPT user ID and workspace-account status, and reads current credentials for each request. This is a useful trusted-side design precedent. Native refresh currently requests unlimited error body and no per-token-endpoint timeout override; product relay must still impose bounded errors/timeouts and redaction. [Identity anchor](https://github.com/openai/codex/blob/01fc69f4026735edfdf6789820549727a4867b11/codex-rs/model-provider/src/auth.rs#L126), [request snapshot](https://github.com/openai/codex/blob/01fc69f4026735edfdf6789820549727a4867b11/codex-rs/core/src/client.rs#L1038).

## Native payload compatibility

The source explains the already retained actual GPT6 fake-provider trace. `model_info.use_responses_lite` prepends an **input item** `{type:"additional_tools", role:"developer", id:..., tools:[...]}`, with namespaced tool definitions when supported; base instructions become an input message; top-level `tools`/empty `instructions` are omitted. Ordinary models use top-level tools. The builder sets `store:false`, `stream:true`, includes `reasoning.encrypted_content`, and preserves native input/history, model, text controls, reasoning, client metadata and prompt-cache key. Lite disables parallel tool calls. The Lite header is sent with this payload. [Builder](https://github.com/openai/codex/blob/01fc69f4026735edfdf6789820549727a4867b11/codex-rs/core/src/client.rs#L885), [wire structure](https://github.com/openai/codex/blob/01fc69f4026735edfdf6789820549727a4867b11/codex-rs/codex-api/src/common.rs#L278).

A narrow relay should validate scope/model/method/body bounds and then forward the native payload without rebuilding it through Corenius `DirectProvider`'s reduced function-tool type. It must retain SSE terminal/error semantics, item/call IDs, custom code-tool calls/results, encrypted reasoning and turn-state response headers. For an HTTP-only profile, pin `supports_websockets=false`; source compresses request bodies only for enabled first-party backend auth, so the ordinary sterile custom provider takes the uncompressed path. This source audit plus prior actual fake-provider execution establishes the client wire shape, **not live backend acceptance or model entitlement**. Custom providers also intentionally strip some first-party internal message/tool metadata; exact first-party feature parity is not claimed.

| Public API key / organization gateway | Public Responses or fixed organization gateway; API key or gateway credential, optional project/org policy | Official gateway docs permit Responses-compatible custom providers. ## Actionable06 contract and remaining qualification

Inference/design recommendation: expose only a scoped local Responses service to sterile native realms; keep upstream auth, storage, refresh and workspace discovery in one trusted owner. Bind credential reference + account/user identity + auth generation + approved backend origin/routing + allowed model to the registered runtime. The inbound native request must not select an upstream URL, credential source, account, refresh endpoint or arbitrary header. Overwrite authority headers, reject redirects, preserve only bounded native compatibility headers, pass the native JSON/SSE representation, and define stream disconnect/retry/unknown outcomes without blind duplicate inference.

A fixed-origin relay must either bind the approved origin selected by trusted workspace discovery or explicitly refuse unqualified routing. It cannot silently hardcode the default for every account, nor turn discovery results into a worker-controlled forward proxy. If access expires, perform serialized same-owner refresh/reload before retrying a definitively rejected401; after stream output or ambiguous transport loss, preserve the interrupted/unknown outcome and reconcile instead of restarting a turn.

Reusable upstream implementation seams exist (`codex_login::AuthManager`, `codex_model_provider::auth_provider_from_auth_manager`, provider/workspace routing), but internal Rust APIs are not a declared stable remote auth-broker interface. No ready-made safe Corenius wrapper is established. Product06 still needs the credential owner/coordination contract, fixed-route wrapper, scoped callers, bounded streaming/errors, negative credential/header/redirect/routing tests, and then owner-authorized actual provider qualification. Neither credential absence nor source absence is the blocker: implementation and qualification remain. The earlier hidden `responses-api-proxy` and existing `DirectProvider` remain insufficient for the reasons in `prior-readiness.md`.
