Weng harness course · Lesson 6 of 10

Self-improving harnesses

Matching Weng section: Self-Improving Harness. Read the public original.

Learner win

Specify a bounded harness-improvement generation and distinguish immediate harness gain from recursive successor gain.

Code is a broad representation

Executable code can represent prompts, tools, memory, permissions, control flow, and subagents. That breadth enables useful edits and enlarges the attack surface. A safe generation declares the parent, editable files, evidence, candidate delta, evaluation, integrity checks, and external promotion decision.

Keep authority outside the editable loop

The evaluator, hidden tests, permissions, complete root-tree budget, rejected-candidate archive, and promotion authority must not be candidate-writable. A prompt that says “do not edit” is not an enforced boundary.

An accepted harness that beats its parent supports immediate harness gain. Successor recursive gain requires a later matched test showing that the accepted child produces better valid successors than its parent under the same proposal and selection envelope.

Source cards

  • STOP self-applies LM-calling improver code while the language model remains fixed.
  • SELF-HARNESS uses a bounded propose–evaluate–accept loop over model-specific harness edits.
  • HARNESS-DISENTANGLE asks whether an update activates, is followed, and benefits the task agent.
  • AHE grounds edits in traces and requires predicted effects, while protecting runs, verifier, and model configuration.
  • WENG-REWARD warns that optimization can exploit proxy evaluators rather than improve the intended capability.

Card recall and boundary check

Card recall: Pick STOP, Self-Harness, or AHE. State the edited object, fixed model boundary, evaluator, and strongest supported claim.

Boundary check: A candidate improves held-out score but edits the test runner and hides two rejected branches. List the integrity failures before discussing task gain.
