## Current fencing and its restore limits

`storage::active` requires configured Broker epoch equal the deployment active epoch. Authentication additionally checks credential epoch and DB expiry; Worker/Verifier task generation checks, command preconditions, cache scope and live authorization remain mandatory. Artifact, supervisor, gateway and Temporal operations apply those fences. Gateway checks current admission generation/epoch even for Owner, so stale-epoch journal recovery is not an existing special Owner API. Supervisor's current Owner historical recovery only applies when the old row remains present.

`Broker::rotate_epoch(old_owner, new_epoch)` rejects same/reused epochs in the current DB, records a chosen epoch and updates active state transactionally, then issues a new Owner token. It is a useful normal-operation primitive, not a dispatch-disabled restore procedure: allocation is supplied by the caller, epoch history is inside the backup, and current API has no restore inventory/authorization checkpoint. Restoring active_epoch and old unexpired credentials can make them valid again if services reopen with the restored epoch. Therefore freshness must come from control state outside the restored backup or a new unguessable identity, persisted before listeners/dispatch reopen. Generating a new value only from restored counters/history is insufficient. The normal rotate API issuing a token does not authorize agents or dispatch before reconciliation.

Epoch checks fence subsequent broker writes, not an RPC already received by a provider or arbitrary shell effects. Old gateway connections, native continuation and physical jobs need separate transport/execution reconciliation. `GatewayOperationDriver` must not repeat an uncertain Start merely because an Activity, workflow or restored operation lease appears retryable. Restored journals may incorrectly say prepared or omit an already-executed operation; independent inventory must be consulted before permitting a new effect. Temporal old-generation Activities are rejected by current bridge fences only after the new epoch/current registry policy is applied. Workflow timers/history are not external-effect absence proof.

## Artifact retention and admission closure during restore

RestoredPG can lose a candidate/report/log reference created after the backup while its immutable bytes survive. Current `ArtifactService::collect` uses `artifact_objects` presence as its non-staging protection criterion. If rollback removes that row and grace elapses, current collection can remove those bytes as apparently unreferenced. Grace age alone cannot distinguish a genuinely unreferenced publication orphan from a lost post-backup reference. `read_evidence` also needs restored task/reference authorization; direct immutable-store access proves bytes, not permission or accepted state.

Future24 must keep collection closed or establish a recovery-boundary retention protection until independent inventory/reference retention is reconciled. Dispatch/new admission must likewise remain closed where inventory coverage is unknown; new budget counters cannot treat vanished reservations as free capacity. Referenced candidates/checkpoints and raw private traces need separate retention/redaction rules. This is a consequence of canonical retention/unknown-inventory requirements, not a new storage architecture or approval to rewrite accepted schemas.

- A public restore/readiness state machine must keep dispatch, admission, collection and credential reissue behind an explicit owner authorization checkpoint. No such restore command/checkpoint or inventory-coverage read model exists in accepted15. Failure must preserve authorized inspection/recovery, not turn an incompatible schema into permission to launch.
- A recorded consistent backup boundary must correlate brokerPG, Temporal state/configuration and all protected artifact digests. Accepted schemas/migrate functions provide version checks and transactions, not that cross-service boundary, backup CLI or interrupted-upgrade/rollback recovery procedure. Runtime/migration credential separation remains to implement operationally.
- Complete independently discoverable environment/provider/controller inventory must include unknown/post-backup jobs and operations, full origin/identity/scope evidence, coverage and explicit disposition. Placement/format/authority of that surviving inventory is an unresolved future24 implementation contract; this note does not choose another execution authority or a new backend.
- Adoption must bind new current authority to original proven execution, generation, store and immutable evidence; stopping must establish complete effects stopped before conflicting capacity refund. Unknown/unreachable/lost-origin entries are quarantined and accounted for. There is no accepted orphan adopt command; no restored SQL row or shell output may invent its proof.
- Provider control ownership, native continuation and store aliases need an explicit single-host reconciled transfer. Accepted gateway permanently fences a replacement controller until old control is proven inactive; no recovery lease expiration or empty lossy history can replace that proof. Unsupported provider-wide observation is a named coverage limitation that keeps the target closed.
- Post-backup artifacts and workflow incarnations require retained mappings and evidence binding. Existing byte integrity, known-workflow observation and replay tests do not prove reconstruction after PG rollback. Optional Kata/jj backends stay outside this accepted baseline; no compatible adopted-backend backup guarantee is inferred.

Accepted schema0005 is immutable implementation history now: future changes must use additive/version-guarded migrations after then-accepted dependencies, not silently edit0005. Ticket16 should claim restart recovery only when demonstrated and must not advertise full restore inventory from these existing primitives.

## Proposed public restore drill oracle

This sequence is a future test contract derived from ticket24/SPEC, not executed evidence or implementation permission. Use disposable loopbackPG, realTemporal/SDK histories, real isolated Git/artifact storage and actual bwrap jobs plus deterministic fresh-effect runtime. The approved [model-free fixture bounds](../decisions/20261001-approved-baseline.md) are 2 concurrent attempts, 8 total admitted episodes, at most3 repairs and 30-second episode deadlines, zero model calls. Smaller bounds may be used; this note grants no larger episode budget.

| Drill boundary/action | Public observation required after restore |
| --- | --- |
| Before boundaryB, admit mission/task and capture a consistent broker/workflow/artifact backup with actual boundary IDs/digests | Backup manifest identifies what it protects and what was not captured; no claim based only on dump exit0. |
| AfterB, create another admitted job/operation and credential/reference, start actual nested/background effects, independently retain full inventory origin/identity/coverage | Post-backup job is provably running before restore and absent from restored registry; heartbeat/effect IDs demonstrate a real survivor rather than a fabricated orphan row. |
| RestoreB while retaining that job/controller/runtime store, old token and post-backup immutable bytes | New fresh epoch comes from outsideB and is persisted before access; public status reports dispatch/GC/admission disabled and unknown inventory/capacity; old token fails read, mutation and cached-response paths. |
| Reconcile through future authenticated recovery inventory API | Public inventory reports the real post-backup handle/controller/operation even though restoredPG did not know it; full authority/membership proof establishes stopped/adopted or explicit quarantine; missing coverage leaves target closed and holds conflicting capacity. |
| Retry restored prepared intent or attempt to launch new conflicting work | Actual per-RPC invocation/effect count does not increase for an uncertain duplicate; no silent new Create on lost-ID case; surviving owner/transport cannot race a replacement controller. |
| Resolve retention while attempting GC and candidate acceptance | Post-backup referenced candidate/log/checkpoint bytes remain protected while references are unresolved; corrupt/missing protected bytes block readiness/acceptance; no old report accepts a changed base/spec/candidate. |
| Prove stop or explicit evidence-backed adoption, then owner checkpoint/reissue | Only now does dispatch reopen for reconciled targets; budget/reservation accounting includes survivors, explicit dispositions and zero fabricated refunds; supervised deletion and slot refund occur once after provedStop and completed deletion. |
| Inject incompatible schema/workflow history, interrupted upgrade or rollback; make runtime inventory unavailable | Public errors/readiness expose incompatibility/unknown, keep dispatch and collection closed, retain recoverable evidence; no accepted-schema rewrite, unsafe workflow restart or unmeasured RPO/RTO claim. |

Oracles must use authenticated command/read projections, immutable bytes, authoritative runtime observations, actual process identity/group proof, independent invocation/effect records and SDK replay. A direct SQL update setting stopped/accepted or a fake count cannot be the recovery verdict. Closing an operator view or killing an agent is not the rollback drill; preserve actual external survivors across restoration. With live provider inventory unavailable, the correct expected result is quarantine/closed coverage, not a claimed adopted execution.
