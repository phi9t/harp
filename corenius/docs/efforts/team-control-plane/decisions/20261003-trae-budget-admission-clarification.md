# Clarify synthetic repair admission and failure accounting

Commit read: a008c33a4fc00f473ab90d452118091655c19742. This supplements the synthetic repair decision; it does not replenish or widen its two-incarnation/three-turn/three-incoming-request acceptance envelope. Independent critique is retained in research/trae-budget-repair-independent-critique.md. Preparation remains offline and runtime admission is withheld.

Count an incoming HTTP request at the owner-controlled guard before route or body parsing; include discovery, malformed, denied and retry requests. Record transport connections separately. At most three requests can be admitted/forwarded to the owned synthetic response implementation, using one durable ledger shared across both potential incarnations. A fourth incoming request is a measured contract violation and stops the round, not a permitted fourth request or a hidden success. Proxy refusal/async process stop cannot prove no fourth client attempt. Acceptance must observe no extra requests after exact whole-namespace shutdown, and separately describe the forward limit and transport coverage. This synthetic design is not a guarantee about external generation/billing.

Before runtime admission freeze exact case-to-turn/incarnation mapping. Required cases remain retryable HTTP error, stream truncated at a specified event boundary, and valid successful terminal response. All discovery consumes the same three requests: if discovery exhausts available slots, stop and report incomplete coverage; no additional allowance. Do not launch a second incarnation after request budget is exhausted. An expected test-induced error may proceed to the next planned case only with exact terminal failure, no retry and no uncertain external effect. Unexpected retry, metadata/config rejection or unclassified outcome ends the round; no guessed replacement provider.

Reserve before any upstream or response-producing effect; never refund on error or restart. On request three revoke further admission before writing the final response. Observe runtime terminal outcome within the existing timeout, then stop the exact namespace and inventory every member. If no terminal outcome appears, stop on deadline and report uncertainty; do not fabricate completion. Any further incoming attempt is recorded as failure and triggers immediate stop even while the final response is pending. Require both event sequence and exact runtime content/terminal evidence for successful streaming, not merely HTTP200.

Offline public fixtures and frozen design must reconcile every critique item: concurrent last slot, malformed/oversized/chunked/missing or inconsistent body length before unbounded read, atomic owner-only ledger and immutable attribution, crash/restart without resetting counters, second-incarnation shared ledger, fourth-attempt zero forwarding, response-byte cap, namespace descendant/timeout handling, no external egress, retry/model/cap configuration and event identities. Mock clients do not prove pinned Trae retry suppression. Root may admit only the reviewed runnable candidate; no launch authority exists from a proposed key or passing mock test.
