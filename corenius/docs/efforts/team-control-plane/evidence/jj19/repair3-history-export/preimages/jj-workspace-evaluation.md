## Outcome and recommendation

All five final behavior slices passed, and all five unsafe public controls failed at their intended behavioral assertion. The evaluation uses an executable, disposable shim exposing create_attempt, inspect, checkpoint, freeze_candidate, prepare_integration and release. It does not install a production workspace service or change kernel/provider/workflow/schema behavior. Every attempt starts in its own repository store at a recorded exact base; one trusted fixture writer owns every disposable workspace. The peer shared-store case deliberately measures unrestricted raw CLI authority.

The results show jj can preserve immutable exported candidates and recover a specific interrupted checkout, while its convenient defaults add authority-sensitive behavior. Status snapshots edits; shared workspaces can rewrite each other's changes; no-snapshot status can reconcile repository operation heads; ignored tracked content remains captured; successful Git export can leave a conflicted bookmark's old Git ref. These require explicit service authorization, exact-operation inspection, private/path/type validation and pre-export ambiguity rejection. No measured reduction in lost work, recovery effort or integration cost was established against Git. The earlier Git-first recommendation reflected that limited measurement. The current preferred-candidate direction still needs explicit qualification and root reconciliation. Any ticket 25 implementation requires authority for its production broker integration, pin/toolchain maintenance and security review.

In that green run, zero-based command event 30 executes `/usr/bin/python3 verify_jj_candidate.py --expected original` in a separate exported Git checkout with its own private home/config/cache. Event 31 journals the forthcoming content rewrite only after the passing receipt is stored and fsynced. The fixture then snapshots the changed content and actually attempts reuse of that old receipt: refused. Event 53 independently runs `--expected changed`, binds a fresh receipt, and reuse for that exact candidate succeeds. Event 59 independently reimports the unchanged original bundle and runs `--expected original` again. A later description-only rewrite keeps the tree but changes the commit and refuses the changed receipt.

Each content-addressed receipt binds exact candidate commit/tree/base, specification SHA256 `eea32d2c1eae575e6d9c6de1e2317fe36a8cd0c945b29375346511df05638040`, acceptance-suite SHA256 `f32acf99ce7f95338e9dc5801019fd82953a52b1ec906aa5802d0efedffcf9b4`, the full verifier environment and its digest, exact command, exit/stdout/stderr and a distinct verifier checkout. The fixture checks the stored receipt digest and context before reuse. This is independent execution in the evaluation, not an authenticated security role: processes share the host UID.

Both bundles and all three receipts survive fixture cleanup in [retained-candidate artifacts](../evidence/jj19/repair1-verification-binding/final-retained-candidate-artifacts/verification-original-before-rewrite.json). ## Limits and dependent handoff

Private home/config/cache and disabled inherited Git configuration/hooks were used. Deliberate local hook tests are owned disposable fixtures. Separate repository stores avoid cross-attempt mutable sharing; this evaluation does not prove a mediated shared-store authorization service. No throughput or comparative human-effort benefit was measured.
