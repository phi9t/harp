## Integration seam and limits

`Bridge::{register,lookup,enqueue,apply_with_capability,progress,next,close,pending_wakeups,deliver,operation_journal}` are public Rust commands/reads. `BridgeActivities::with_operation_driver(Arc<dyn OperationDriver>)` registers actual Activity-side operation work. `GatewayOperationDriver::new(bridge,gateway,bearer,runtime)` queries exact journals and delegates only prepared operations to accepted Gateway; uncertain states never cause redispatch. Kernel16 must explicitly provision runtime/store binding and prepare Create/Start intents with accepted Gateway commands, then register that driver on worker Activities. No configured driver reports `operation_driver_unconfigured`; missing binding/intent reports `gateway_binding_or_intent_missing`; closed orchestration reports `workflow_closed`. None means provider completion or task acceptance. Actual provider binding/mission lifecycle assembly stays ticket16.

The worker's Activity credential map is explicit local capability provisioning; deployment credential issuance and lead-session replacement are later seams. Recovery epoch rotation requires recovery orchestration to retire/allocate registry generations explicitly; this slice does not auto-reopen a live registry or claim multi-host failover. Gateway remains single-host fail-closed; no DB-check-then-RPC exactly-once or live Trae guarantee. Runtime cancellation/transport fencing remains gateway/supervisor responsibility; close does not revoke an already executing RPC. Three selected histories are retained, not every intermediate run.

Shared glue is exactly Cargo.toml/Cargo.lock, lib.rs temporal export, storage.rs transaction-local command application and migration call, and the gate shim selecting the real Temporal runner. New owned paths are temporal.rs,0004.sql,tests/temporal.rs,tests/run-temporal.sh and this evidence. Migration0005 and supervisor code were untouched.
